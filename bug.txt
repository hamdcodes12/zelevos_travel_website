Title:
Navbar Search Button Inactive Due to Missing Target Element Reference

Date:
23 September 2026

Module:
Customer / Navigation & Global Search

Page:
Global Header Navbar (.search-button)

Severity:
MEDIUM

Status:
VERIFIED

How to Reproduce:
1. Open the homepage (http://localhost:3000/).
2. In the desktop header navbar, locate the search icon button (.search-button) adjacent to the user menu badge.
3. Click the search button.
4. Observe that no input is focused, no modal opens, and nothing happens on screen.

Expected Result:
Clicking the search button in the navbar should open an interactive search experience (Global Search Spotlight Modal) or smoothly focus the search field with destination shortcuts and package filters.

Actual Result:
Clicking the search button did nothing. The button click was completely dead.

Error:
Silent JavaScript failure: document.querySelector('#hero-input') evaluated to null.

Root Cause:
1. In artifacts/zelevos/src/App.tsx (line 591), the onClick handler for .search-button was originally written as:
onClick={() => document.querySelector<HTMLInputElement>('#hero-input')?.focus()}
However, the hero input in the DOM was actually assigned id="hero-destination-input". Because '#hero-input' did not exist in the DOM, the optional chaining operator (?.) caused the expression to fail silently with null.
2. In addition, when GlobalSearchModal was initially introduced, it was instantiated inside <header className="navbar">. Because .navbar has CSS `backdrop-filter: blur(20px)` and a fixed height of 73px, according to the CSS filter/transform specification, .navbar formed a new containing block for position: fixed descendants. Consequently, .global-search-backdrop was constrained to the 73px header instead of the 100vh viewport, causing the search modal to be pushed down by its padding and clipped so that only the top 15px sliver of the input box peeked out at the bottom edge of the navbar.

Files Changed:
- artifacts/zelevos/src/components/global-search-modal.tsx
- artifacts/zelevos/src/App.tsx
- artifacts/zelevos/src/index.css

Fix Applied:
1. Implemented React createPortal(..., document.body) in GlobalSearchModal so that the search modal is guaranteed to mount directly under document.body, completely isolated from any parent container, overflow constraints, or backdrop-filter containing blocks.
2. Wrapped Navbar's return in a React fragment (<> <header>...</header> <GlobalSearchModal /> </>) to structurally place the modal outside <header>.
3. Added body scroll locking (document.body.style.overflow = 'hidden') while the search modal is open to ensure pristine luxury app UX.
4. Upgraded CSS in index.css:
   - .global-search-backdrop: position: fixed; inset: 0; width: 100vw; height: 100vh; z-index: 9999999 !important; background: rgba(10, 25, 47, 0.76); backdrop-filter: blur(12px);
   - .global-search-dialog: width: min(100%, 680px); max-height: calc(100vh - 120px); border-radius: 20px; box-shadow: 0 30px 80px -15px rgba(9, 31, 71, 0.5); z-index: 10000000;
5. Created full feature set: auto-focused search input, popular destination chips (Kashmir, Ladakh, Kerala, Rajasthan, Goa, Himachal, Andaman), category shortcuts (Flights Concierge, Build My Trip), live search results with package images and pricing, and a "Jump to Home Search Bar" button.

Verification:
1. Ran live Chrome diagnostic (scripts/diagnose-modal-position.mjs) on 1536x826 viewport:
   - Verified backdropParent changed from "HEADER.navbar" to "BODY."
   - Verified backdrop dimensions expanded from 110px to full viewport: width: 1536px, height: 826px, top: 0, bottom: 826px.
   - Verified dialog is perfectly centered at x: 428px, y: 66px, height: 377.5px, bottom: 443.5px with zero clipping.
   - Captured full-screen screenshot (search_modal_fixed_full.png) proving 100% visibility of the entire modal.
2. Ran live Puppeteer test in scripts/test-navbar-search-fix.mjs:
   - Clicked #navbar-search-btn: confirmed modal opened and #global-search-input auto-focused.
   - Typed query "Kashmir": confirmed real-time package filtering.
   - Clicked destination pill "Kerala": confirmed modal closed and page filtered to Kerala.
   - Tested Ctrl+K keyboard shortcut: confirmed modal toggled on/off.
   - Tested ESC key: confirmed modal closed cleanly and restored body scroll.
   - Tested "Jump to Home Search Bar": confirmed smooth scroll to hero and active focus on #hero-destination-input.

Title:
Customer Package Checkout Allowed Without Authentication Gate Leading to 401 Error

Date:
23 September 2026

Module:
Customer / Booking & Checkout Engine

Page:
Homepage / Package Detail Modal / Package Checkout Modal

Severity:
HIGH

Status:
VERIFIED

How to Reproduce:
1. Open website as an unauthenticated visitor (incognito / logged out).
2. Click "View & Book" on any curated package (e.g. Kashmir Luxury Retreat).
3. In the Package Detail Modal, click "Book This Holiday" (#book-now-package-btn).
4. Observe that PackageCheckoutModal opens without requiring sign-in.
5. Fill details and click "Pay securely with Razorpay" (#confirm-pay-btn).
6. Observe that the API rejects with 401 Unauthorized ("Authentication required"), displaying a raw error message and blocking the customer from completing their purchase.

Expected Result:
When an unauthenticated guest clicks "Book This Holiday", the system should gracefully prompt them to log in or create an account with a friendly notice ("Please log in or create an account to book your holiday package."). Once authenticated, the checkout modal should open with the customer's name and email pre-filled.

Actual Result:
Guest was allowed to fill the full checkout form unauthenticated, after which submission failed with a 401 error. The form also defaulted to dummy placeholder data ("Aarav Sharma") instead of the authenticated customer's profile.

Error:
HTTP 401 Unauthorized from POST /api/bookings: { "status": "unauthorized", "message": "Authentication required" }

In artifacts/zelevos/src/App.tsx, the onBook callback passed to PackageDetailModal directly invoked setSelectedPackageSlug(null) and setCheckoutPackage(pkg) without checking if (user). Unlike openBuildMyTrip (which checked if (user) and invoked openAuth), package booking lacked the authentication gate. In addition, PackageCheckoutModal did not accept user or onLogin props, preventing profile auto-population and graceful inline auth prompts.

Files Changed:
- artifacts/zelevos/src/App.tsx
- artifacts/zelevos/src/components/package-checkout-modal.tsx

Fix Applied:
1. In App.tsx, updated PackageDetailModal's onBook callback: if (!user), it calls openAuth('login', 'Please log in or create an account to book your holiday package.', callback) so that after signing in, checkout opens automatically.
2. In package-checkout-modal.tsx, updated PackageCheckoutModal to accept optional user and onLogin props.
3. Pre-populated fullName with user?.fullName and contactEmail with user?.email.
4. Added defensive 401 response handling in handleCheckout to trigger onLogin() and show a helpful prompt if session expired.

Verification:
1. Ran live Puppeteer test in scripts/test-checkout-auth-gate.mjs.
2. As unauthenticated guest, clicked "Book This Holiday": verified auth dialog opened with context notice "Please log in or create an account to book your holiday package."
3. As authenticated customer, executed complete lifecycle in scripts/test-complete-customer-flow.mjs: verified booking was created with HTTP 201 Created and master booking ID (e.g. ZL260923001).
4. Verified booking appeared in /bookings/my-trips and individual trip detail query.

Title:
Partner Registration Schema Inflexibility Rejecting Standard Partner Payloads

Date:
23 September 2026

Module:
Authorised Partner / Registration & Approval

Page:
Public Partner Application Modal & Backend Endpoint /api/partners/register

Severity:
MEDIUM

Status:
VERIFIED

How to Reproduce:
1. Send a POST request to /api/partners/register with payload containing agencyName, contactPerson, email, and phone.
2. Observe that the server returns HTTP 400 Bad Request with validation error: "Invalid input: expected string, received undefined" at path ["contactName"].
3. Also observe that upon Admin approval (/admin/partners/:id/approve), if the administrator sets commissionRate, the commission_rate_percent column was not updated.

Expected Result:
1. The partner registration endpoint should accept both contactName and contactPerson interchangeably to prevent validation failures across different client integrations.
2. The admin approval endpoint should persist the administrator's specified commissionRatePercent.

Actual Result:
1. Standard partner payloads sending contactPerson were rejected with 400.
2. Admin approval updated status to "approved" but ignored commissionRate in the request body.

Error:
HTTP 400 Bad Request: { "status": "invalid_request", "message": "Provide valid partner registration details.", "errors": [{ "code": "invalid_type", "expected": "string", "path": ["contactName"] }] }

Root Cause:
In artifacts/api-server/src/routes/partners.ts:
1. The Zod schema strictly defined contactName: z.string() without an alias or fallback for contactPerson.
2. The POST /admin/partners/:id/approve route only updated { status: "approved", updatedAt: new Date() } and did not check or apply commissionRate / commissionRatePercent from req.body.

Files Changed:
- artifacts/api-server/src/routes/partners.ts
- artifacts/api-server/dist/index.mjs (rebuilt)

Fix Applied:
1. In partners.ts, updated the Zod schema for /partners/register to allow contactName and contactPerson interchangeably:
   contactName: z.string().trim().min(2).optional(),
   contactPerson: z.string().trim().min(2).optional(),
   with a refine check ensuring at least one is provided, and extracted contactName = (data.contactName || data.contactPerson).trim().
2. In /admin/partners/:id/approve, added logic to extract commissionRate = req.body?.commissionRate || req.body?.commissionRatePercent, and if provided, persist it as commissionRatePercent in partnersTable.
3. Rebuilt api-server (node ./build.mjs) and restarted server process.

Verification:
1. Executed scripts/test-complete-partner-lifecycle.mjs with contactPerson: 'Suresh Raina'.
2. Registration succeeded with HTTP 201 Created, status "approved", and unique referral code.
3. Admin authenticated and approved partner with commissionRate: 8: verified partner status updated to "approved".
4. Verified partner directory in Admin /admin/partners.

Regression Tests:
- scripts/test-complete-partner-lifecycle.mjs (PASS)
- scripts/master-regression-test.mjs (PASS)

Related Features Retested:
- Public partner registration form (PartnerRegistrationModal)
- Admin partner network tab & commission ledger
- Partner referral code generation and format
